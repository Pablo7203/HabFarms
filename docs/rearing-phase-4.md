# DOC Phase 4 — Reporting and reconciliation (completion in progress)

## Implemented locally

- `/rearing/reports` provides batch/date-filtered daily activity, a Monday-start weekly rollup, missing daily-record indicators, and a same-cutoff lifecycle snapshot. Population and cost use the same as-of date.
- The daily report is generated by `get_rearing_daily_report`; each selected date is pre-aggregated independently to avoid multiplying mortality, feed, health, or expense totals through joins. Dates before the batch arrival are excluded from the final report API.
- The reconciliation panel uses `get_rearing_reconciliation` and compares population, mortality, feed quantity/cost snapshots, health-cost sources, accumulated cost, transfer source/destination movements, transfer cost, and reversals. It never writes or balances operational records.
- The portfolio shows net birds transferred from source movement records and reports rearing survival as `(remaining birds + net valid transferred birds) / initial chicks`. The batch detail uses the same survival definition.
- CSV route types now cover rearing portfolio, daily/weekly summaries, mortality, feed, health, batch cost, transfer history, lifecycle snapshot, and reconciliation. The portfolio export is as-of date aware; history exports are farm/batch/date filtered; worker responses omit cost columns; cell escaping protects spreadsheet-formula prefixes.
- `202609230056_rearing_phase4_as_of_summary.sql` adds a role-shaped effective-date snapshot. `202609230057_rearing_phase4_reconciliation_sources.sql` adds independent source comparisons and validates both sides of a transfer reversal. The unused local variable in pending Phase 3 migration `046` was removed; this is a no-behavior-change lint cleanup.

## Definitions and sources

| Measure | Definition / source |
| --- | --- |
| Initial chicks | `rearing_batches.initial_quantity`; initial receipt is represented once by the arrival movement. |
| Remaining birds | Signed sum of the batch's `rearing_movements` through the selected day. |
| Deaths | Death movement quantity; an audited reversal appears as an inbound movement, so both are shown in the daily movement equation. |
| Transferred out | Source `transfer_out` movements. A reversal is separately represented by an inbound `transfer_reversal`; transfer history status remains authoritative for net valid transfer totals. |
| Rearing survival | `(current rearing birds + net valid transfers) / initial chicks * 100`; post-transfer layer mortality does not change it. |
| Feed quantity/cost | Active batch feed-consumption links joined to the authoritative farm feed movement and immutable movement cost snapshot. Purchases and supplier payments are not added. |
| Completed health activities | Active `health_records` on the selected batch/date. Due reminders remain a separate scheduled count. |
| Attributable daily cost | Feed consumption snapshot cost plus active batch-linked expenses on the expense date. Health-service cost is included only through its linked expense source to avoid counting the health record and its expense twice. Cash paid is not included. |
| Daily completeness | `submitted` if a `rearing_daily_records` row exists; otherwise `missing`. An independently recorded feed or health event does not mark the daily record submitted. |

All dates use farm event dates and the existing farm timezone for default date selection. Weekly groupings start Monday and may be partial at either end of a custom range. Transfer reversals are compensating population movements dated to the original transfer date; therefore an approved reversal updates the effective-date history from that date, while `reversed_at` and audit timestamps retain when the correction was performed.

## Reconciliation status

Results use `RECONCILED`, `DISCREPANCY`, `INSUFFICIENT SOURCE DATA`, or `NOT APPLICABLE`. A status is diagnostic only: no artificial movement, expense, payment, or cost adjustment is created.

## No-plan and pre-arrival reporting behavior

- Planned-versus-actual feed reporting keeps `planned_kg` and `variance_kg` null when no effective feed plan exists for that date/product. Actual ledger consumption remains visible; the UI says “Not configured” / “No plan configured” instead of rendering a false zero target or variance.
- A lifecycle cutoff before the selected batch's arrival is not applicable, not an incomplete-cost result. The report shows “Batch not yet arrived” and does not infer zero population or cost. The lifecycle CSV endpoint returns a specific explanation rather than calling the as-of RPC with an invalid date. The RPC continues to reject pre-arrival dates for direct callers.
- These corrections are in forward migration `202609230058_rearing_feed_variance_null_plan.sql` plus the reporting/export UI. They are local changes only; verify remote migration history before deploying this migration and app change together.
